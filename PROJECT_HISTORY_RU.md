# Seeding Detection: история проекта, текущее состояние и план до защиты

Дата актуализации: 20.02.2026

## 1. Контекст дипломного проекта

Проект Seeding Detection развивается как прикладной прототип для анализа сеянцев и растительного материала на изображениях и PDF.  
Цель диплома: показать рабочий инструмент с автоматизацией ключевых операций (детекция, измерения, отчёт), понятной архитектурой и воспроизводимыми результатами.

Важно: это не промышленный продукт. Для диплома приоритетны:
- стабильная демонстрация основных сценариев;
- чистая и понятная структура кода;
- внятная документация и тесты на критические части;
- управляемый объём функционала без перегруза.

## 2. Эволюция проекта по этапам

### Этап 0. Ранние версии (3.1-3.2, legacy)

Что было:
- монолитный `main_window.py` с UI и бизнес-логикой в одном месте;
- базовые операции: открытие файла, детекция, просмотр, сохранение отчёта;
- неполная отказоустойчивость по части координат, путей, прогресса;
- устаревшая и частично расходящаяся с кодом документация.

Основные проблемы legacy:
- рассинхрон bbox после поворота;
- выход координат кропа за границы;
- слабая валидация путей к весам;
- пустые страницы в PDF при безусловных переносах;
- неоднозначное поведение при выборе пути отчёта;
- перегруженный UI и визуальная неоднородность.

### Этап 1. Стабилизация и исправление критических ошибок

Что сделано:
- исправлен поворот bbox и синхронизация с изображением;
- добавлен клиппинг координат;
- улучшена кроссплатформенная проверка путей;
- улучшен PDF pipeline (без лишних пустых страниц);
- обновлены README и базовая документация;
- добавлены тесты и CI-проверки.

Результат:
- версия стала пригодной для стабильной ежедневной работы;
- уменьшен риск аварий в критических пользовательских сценариях.

### Этап 2. Расширение 4.0 (архитектура + UX + функции)

Что добавлено:
- упорядочены ключевые слои: `controllers.py`, `services.py`, `models.py`, `storage.py`, `utils/`;
- UI расширен панелями статистики и миниатюр;
- все основные инструменты и действия собраны в левом toolbox;
- добавлены экспортные форматы (`JSON/CSV/COCO/YOLO`, экспорт с аннотациями);
- добавлен локальный кэш детекции/классификации;
- добавлена история измерений и экспорт истории;
- добавлен инструмент линейки на canvas (`M`);
- добавлены новые тесты и обновлён CI.

### Этап 3. Текущая доработка устойчивости (последние правки)

Исправлено:
- падение `_active_tool` в `eventFilter`;
- устойчивость `find_all` при `None` progress dialog;
- проблема темы с `icon:/primary/...` (по умолчанию локальный QSS, `qt-material` опционально);
- расширена локализация ru/en для дерева, статистики, миниатюр.

Добавлено в тесты:
- регресс-тесты устойчивости окна;
- тесты локализации UI-панелей.

## 3. Что реализовано на сегодня

### 3.1 Функции пользователя

- загрузка изображений и PDF;
- детекция на текущей странице и пакетная детекция по всем страницам;
- просмотр боксов и дерева слоёв;
- классификация частей объекта;
- измерения из дерева и инструментом линейки на canvas;
- поворот, масштабирование, навигация;
- генерация PDF-отчёта;
- экспорт результатов в несколько форматов;
- кэширование результатов и очистка кэша;
- статистика по объектам и миниатюры для навигации;
- светлая/тёмная тема, ru/en интерфейс.

### 3.2 Технические модули (ядро)

- `seeding/main.py`: точка входа;
- `seeding/config.py`: конфигурация и дефолты;
- `seeding/models.py`: dataclass-модели состояния и DTO;
- `seeding/controllers.py`: оркестрация основных сценариев;
- `seeding/services.py`: обработка изображений, экспорт, отчёты;
- `seeding/storage.py`: локальное хранилище (кэш, история измерений);
- `seeding/report.py`: генерация PDF;
- `seeding/utils/geometry.py`, `seeding/utils/paths.py`: утилиты геометрии и путей;
- `seeding/ui/*`: интерфейс и виджеты.

### 3.3 Качество и проверка

- `pytest`: покрытие ключевых сценариев и регрессов;
- `flake8`: статический контроль качества;
- GitHub Actions CI: автоматический запуск тестов и линтера.

## 4. Что используется и как

Язык и экосистема:
- Python 3.10+;
- PyQt5 (GUI);
- NumPy + OpenCV (обработка изображений, геометрия);
- Ultralytics YOLOv8 (детекция/классификация);
- ReportLab (PDF-отчёты);
- PyMuPDF/Pillow (работа с PDF/изображениями);
- pytest + flake8 + GitHub Actions.

Конфигурация и окружение:
- модель можно задавать через аргумент запуска и/или переменные окружения;
- UI-предпочтения и layout хранятся в `QSettings`;
- `SEEDING_USE_QT_MATERIAL=1` включает `qt-material`, по умолчанию используется локальный QSS.

## 5. Что улучшать дальше (реально для диплома)

Ниже только то, что имеет смысл делать для прототипа к защите.

### Приоритет A (обязательно)

1. Упростить и стабилизировать публичные сценарии в UI.
- Сфокусироваться на 4 демо-сценариях: открыть -> детекция -> измерение -> отчёт/экспорт.
- Всё нестабильное или второстепенное скрыть/не показывать в демо.

2. Снизить сложность `main_window.py` без глубокой декомпозиции.
- Оставить файл единым (как вы и решили), но упорядочить методы блоками.
- Выделить повторяющиеся куски в приватные helper-методы.

3. Закрепить отказоустойчивость.
- Добавить ещё 2-3 регресс-теста на реальные падения из практики.
- Проверить закрытие окна во время фоновых операций.

4. Зафиксировать единый сценарий защиты.
- Подготовить набор входных данных;
- Подготовить шаги демонстрации (5-7 минут).

### Приоритет B (желательно)

1. Дочистить локализацию.
- Перевести оставшиеся пользовательские строки в `tr()`.
- Проверить переключение ru/en по всем панелям.

2. Минимизировать шум в интерфейсе.
- Убрать кнопки, которые не нужны для защиты;
- Убрать дублирующие действия из меню/панелей;
- Проверить tooltips и горячие клавиши.

3. Доработать документацию разработчика.
- Кратко описать роли файлов и связи модулей;
- Описать, как запустить проект и тесты в чистом окружении.

### Приоритет C (можно отложить после защиты)

- сложная система партий, сравнение партий;
- БД с полной историей роста;
- продвинутые аналитические графики;
- настраиваемые пользователем горячие клавиши;
- полный переход на Qt `.ts/.qm` pipeline в рантайме.

## 6. Что убрать или не развивать в рамках диплома

Чтобы не расползался scope:
- не пытаться доводить систему до production-уровня;
- не добавлять крупные новые подсистемы (база данных, сервер, облако);
- не расширять меню и диалоги без необходимости;
- не перегружать UI экспериментальными фичами;
- не делать «архитектурную революцию» перед защитой.

Практическое правило:
- если функция не участвует в демонстрации и не влияет на критерии диплома, её лучше отложить.
